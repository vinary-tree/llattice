# Architecture

> **Audience.** Maintainers and integrators who want to understand the shape of the crate and the rationale
> behind it. Theory lives under [theory/](../theory/); this document is about *the code and the crate graph*.

`llattice` is deliberately tiny: **one trait, two methods, a handful of impls, zero dependencies.** Its value
is not in volume of code but in being the *single, shared* place the lattice vocabulary is defined for a whole
family of crates. This document explains the public surface, the bound choices, the generic-vs-concrete impl
strategy, and the leaf-crate position in the dependency graph.

---

## 1. The public surface

The entire API is one trait:

```rust
pub trait Lattice: Clone + Send + Sync {
    /// Least upper bound (⊔): for sets, union; for numbers, max.
    fn join(&self, other: &Self) -> Self;
    /// Greatest lower bound (⊓): for sets, intersection; for numbers, min.
    fn meet(&self, other: &Self) -> Self;
}
```

![The Lattice trait and its built-in implementors](figures/lattice-class.svg)

Every built-in impl realises this trait; the two red boxes (`f64`, `Vec`) carry the lawfulness caveats proven
in [theory/03](../theory/03-lawfulness-and-proofs.md). The complete behavioural contract — order, bounds,
edge cases — is tabulated in [design/03 — semantics](03-semantics.md).

---

## 2. Why the supertrait bound is `Clone + Send + Sync`

The bound `Lattice: Clone + Send + Sync` is a deliberate design choice, not incidental:

- **`Clone`** — `join`/`meet` take `&self` and `&other` and return an owned `Self`. The structural impls
  (`Option`, `HashSet`, `Vec`) must *clone* elements they keep (e.g. `Some(a.clone())` when the other side is
  `None`). Requiring `Clone` lets the generic (parametric) impls be written once, generically.
- **`Send + Sync`** — the primary motivating use is **merging state across threads and replicas** (CRDTs,
  parallel fixpoint engines). A lattice value that could not cross a thread boundary would be useless for that.
  Demanding `Send + Sync` up front means *every* `Lattice` value is safe to share and move between workers, and
  downstream parallel code never has to re-state the bound.

The cost is that a type must be `Send + Sync` to implement `Lattice` — which excludes e.g. `Rc`-based types.
That exclusion is intentional: such types are not the merge-across-workers values this trait is for.

> **Trade-off recorded.** This choice is captured as a one-line rationale here rather than an ADR because it is
> a property of the trait signature itself, visible in the source. The two *cross-crate* decisions (leaf
> extraction, bridge placement) are weightier and do get ADRs — see [adr/](adr/).

## 3. Generic vs. concrete impls

`llattice` mixes two impl styles, chosen per type family:

- **Macro-generated concrete impls** for the primitive numerics. `u8 … i128`, `usize`, `isize` all share
  `join = max`, `meet = min`, generated by one `macro_rules!`:

  ```rust
  macro_rules! impl_lattice_for_numeric {
      ($($t:ty),+) => { $( impl Lattice for $t {
          #[inline] fn join(&self, other: &Self) -> Self { (*self).max(*other) }
          #[inline] fn meet(&self, other: &Self) -> Self { (*self).min(*other) }
      } )+ };
  }
  impl_lattice_for_numeric!(u8, u16, u32, u64, u128, usize, i8, i16, i32, i64, i128, isize);
  ```

  `f32`/`f64` are written out separately because their `max`/`min` are inherent methods with the IEEE
  `NaN` semantics of [theory/03 §6](../theory/03-lawfulness-and-proofs.md#6-f32--f64--lawful-only-on-the-nan-free-extended-reals),
  not `Ord::max`.

- **Generic (parametric) impls** for the structural containers, each constrained exactly as far as it needs:

  ```rust
  impl<T: Lattice> Lattice for Option<T> { … }                       // lifts any lattice T
  impl<T: Clone + Eq + Hash + Send + Sync> Lattice for HashSet<T> { … } // T need not be a lattice
  impl<T: Clone + Eq + Send + Sync> Lattice for Vec<T> { … }            // T need not be a lattice
  ```

  Note the asymmetry: `Option<T>` requires `T: Lattice` (it *recurses* into `T` —
  $`\mathrm{Some}(a) \sqcup \mathrm{Some}(b) = \mathrm{Some}(a \sqcup b)`$), whereas `HashSet<T>`/`Vec<T>` only need element equality, because their
  lattice structure is the *subset/sequence* structure, independent of any order on `T`.

These are genuine **generic (constructor-parametric) impls over the standard library's container types**. The orphan rule permits them
only because `llattice` defines the `Lattice` trait — which is the whole architectural point of the next
section.

## 4. The leaf-crate position

`llattice` sits at the **bottom** of the dependency graph for the `vinary-tree` family. Nothing it needs is
external; everything else depends *on it*:

![Without a shared crate the family hits an orphan-rule diamond; with llattice there is one canonical trait](figures/crate-family.svg)

```text
        libdictenstein   liblevenshtein   lling-llang   duallity   libgrammstein
               │                │              │            │            │
               └────────────────┴──────┬───────┴────────────┴────────────┘
                                        ▼
                                    llattice            (zero dependencies)
                                 trait Lattice { join, meet }
```

`llattice` was **extracted from `libdictenstein`** to break a dependency cycle: `libdictenstein` needed the
lattice vocabulary, and so did `lling-llang`, but each defining its own trait made their `HashSet` lattices
*incompatible* (the orphan-rule diamond of [design/02](02-orphan-rule.md)). Pulling `Lattice` down into a
shared leaf gives the family one trait, one set of impls, and one meaning of `join`/`meet`. A
`HashSet<T>` merged in `libdictenstein` and a `HashSet<T>` merged in `lling-llang` now agree by construction.

The leaf position is enforced by having **zero dependencies** (`[dependencies]` in `Cargo.toml` is empty) and
importing nothing beyond `std`. This is a load-bearing invariant: see [ADR-0001](adr/0001-extract-llattice-leaf-crate.md).

### 4.1 Compile-time trait and run-time provider are separate layers

The family's crates share a second seam beyond this trait: the versioned
**`vinary-tree-interop` resource ABI**. The native `Lattice` trait remains a
compile-time Rust abstraction resolved by monomorphization; `llattice` still
has no runtime dependency and exports no C symbols. Foreign runtimes instead
exchange an immutable `VtResource` that negotiates the distinct
`vt.lattice.val.1` capability. That capability carries owned values and the
operations `join`, `meet`, equality, stable encoding, diagnostics, and bounded
batch folds.

This split preserves both important properties:

- Native Rust keeps a zero-cost, statically dispatched trait and the leaf crate
  remains dependency-free.
- Julia, Raku, and future supported runtimes can implement lattice values
  without pretending a garbage-collected object is a Rust `Clone + Send + Sync`
  value.
- ABI ownership, callback containment, thread declarations, and batching live
  in `vinary-tree-interop`, where all family resources share one protocol.
- The Julia and Raku packages in this repository provide the ergonomic host
  types and adapters. They depend on their language's `vinary-tree-interop`
  package; the Rust crate does not.

The boundary is therefore between *a mathematical interface* and *one portable
runtime representation of values implementing that interface*, not between
llattice and interoperability. [ADR-0003](adr/0003-host-lattice-provider.md)
records the decision, and the [binding architecture](../bindings/README.md)
defines its ownership and concurrency contracts.
